## Point-light element layout (from the code, not from a guess)

`ps_1806620128.dxbc` (disassembled with the repository's `dxbc_disasm`, i.e. `d3dcompiler_47!D3DDisassemble`)
declares `dcl_resource_structured t20, 48` and `dcl_resource_structured t21, 4`, then walks the tile's index list and
loads one 48-byte element per light. The loads and the arithmetic that follows pin four fields:

```
ld_structured r13.xyzw, index, l(0),  t20   ; bytes  0..15
ld_structured r14.xyzw, index, l(28), t20   ; bytes 28..43
ld_structured r11.w,   index, l(44),  t20   ; bytes 44..47

add r13.xyz, r13.xyzx, -v3.xyzx             ; light position - pixel world position
dp3 / rsq / sqrt                            ; distance
add r11.w, -r11.w, r13.w                    ; range  = r13.w - r11.w
div_sat r11.w, r12.w, r11.w                 ; saturate((distance - inner) / range)
mul r13.xyz, r14.yzwy, r13.xyzx             ; radiance = colour * attenuation
```

| offset | bytes | meaning | evidence |
| --- | --- | --- | --- |
| 0 | 0-11 | world position (xyz) | subtracted from the pixel's world position |
| 12 | 12-15 | outer radius / range | `r13.w` forms the attenuation denominator |
| 44 | 44-47 | inner radius (falloff start) | `-r11.w` offsets the distance before `div_sat` |
| 32 | 32-43 | colour (rgb) | `r14.yzw` multiplies the accumulated radiance |
| 16 | 16-27 | not read by this shader | three floats unused here; candidate for intensity/spot data |

Not settled: bytes 16-27, the meaning of the gate fields at 28 (`r14.x`/`r14.y` are tested with `ge 0` and compared
against a constant before the light is applied), and the spot-light array (`t22`), which has its own stride to be read
from a shader that binds it. The four fields above are enough to emit `remixapi_LightInfoSphereEXT`
(position, radius, radiance) and to scale it by the inner/outer falloff.

## Spot-light element layout

`ps_1752881232.dxbc` declares `t20, 48` (point), `t21, 4` (tile indices), `t22, 80` (spot) and `t25, 32`. The spot
element is 80 bytes and the code pins it the same way:

```
ld_structured r18.xyzw, i, l(28), t22   ; gate at 28 (same field as the point light)
ld_structured r19.xyzw, i, l(0),  t22   ; position at 0..11, cone cos at 12
ld_structured r20.xyzw, i, l(44), t22   ; inner cos at 44, direction at 48..59
ld_structured r19.xy,   i, l(64), t22   ; two floats at 64..71, not identified

dp3 r11.w, r19.xyzx, r20.yzwy           ; direction · (light - pixel)
lt r13.w, r19.w, r11.w                  ; r19.w = outer cone cos, r20.x = inner cone cos
```

| offset | point (48 B) | spot (80 B) |
| --- | --- | --- |
| 0 | position xyz | position xyz |
| 12 | outer radius | outer cone cos |
| 28 | gate / chain field | gate / chain field |
| 32 | colour rgb | colour rgb |
| 44 | inner radius | inner cone cos |
| 48 | - | direction xyz |
| 64 | - | two floats, unidentified |

Both arrays share the gate at 28 and the colour at 32, which is consistent with them being the same struct with a
spot-only tail. That is enough to emit `remixapi_LightInfoSphereEXT` (point) and the spot variant: position, radius or
cone, direction, radiance. Still unidentified: bytes 16-27 in both, bytes 64-71 in the spot, and whether the colour is
already premultiplied by intensity (the point-light path showed no separate intensity multiplier, so it is either
premultiplied or baked into the colour value).
