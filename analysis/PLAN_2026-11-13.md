**Why.** Section 3b. Exposure was tuned by eye against the darker sRGB-tagged picture.

**Steps.**
1. Confirm what is active: tone mapping mode Local, `useLegacyACES` true, auto exposure on with EV range -2 to 5.
2. One key per run on `30632051` and `41686139`, 2,500 frames each, `--conf runtime/replay/confs/l1-<name>.conf`:

#### L2 result (2026-11-13, this session)

**Orientation, from data.** The game's main lit family decodes `sample - 0.5`, scales red by the vertex tangent's
handedness `v4.w`, uses green along `-cross(T, N) = N x T`, blue along the shading normal
(`ps_550290354696.asm:53-58`, the same five instructions in `ps_550292531976.asm:56-58` and
`ps_550292544968.asm:73-75`). Remix builds `T = dP/du`, `B = dP/dv` with the sign chosen per triangle
(`math.slangh:415-497`), and decodes the texture as unsigned octahedral (`packing.slangh:324-362`). Our encoder is
the exact inverse of that decode. So the default is **no flip**, and `NIER_REMIX_LIVE_NORMAL_FLIP_Y=1` stays as the
A/B switch. The residual case that cannot be measured from a capture: a mesh whose UV layout is left-handed gets
relief inverted in **both** axes (the game folds that handedness into red), which a Y flip does not express.
Written up in `replay/research-2026-11-13/normal_handedness.md`.

**Detail normal (step 5).** `live_capture.h:1676` takes the normal map only from `roles.normal.slot`; `detail_normal`
is a separate traced role that no path reads as the main normal, so the blotchy slot-4 experiment cannot come back.

**The change (step 6).** `remix_live.cpp:227` is now `env(L"NIER_REMIX_LIVE_NORMAL") != L"0"` (default on, `=0`
rolls back); `live_capture.h:542` default `true`. Gates first: `test_live_normal_map.py` grew case 3b (a run with no

#### T1 progress (2026-11-13, this session): the gate is frozen, the implementation stops at one measured obstacle

**Read first, in the source:** a material handle **is** its hash (`rtx_remix_api.cpp:886`
`auto handle = reinterpret_cast<remixapi_MaterialHandle>(info->hash)`), so DestroyMaterial + CreateMaterial under the
same hash is a genuine in-place swap and the mesh's stored handle stays right. That is the fact T1 stands on.

**Done and kept:**

- The fake runtime now models the material lifecycle: a repeat `CreateMaterial` under a live hash is a `VIOLATION`
  ("the runtime ignores it, so the surface keeps its old textures"), `DestroyMaterial` logs `hash=… id=…`, and the
  destroy-then-create pair is legal. That alone is worth keeping: it is what made the old rebuild path visible.
- `checks/gate_live_late_material.py` (renamed out of the suite until it passes) asserts what T1 must deliver: **one
  build per geometry**, no texture-triggered rebuilds, and a `CreateMaterial → DestroyMaterial → CreateMaterial` triple
  under one unchanged hash whose arguments actually differ. Today it fails with
  `geometry … was built 3 times … [{'materials': 0, 'presented': 0}, {'materials': 2, 'presented': 2}, {'materials': 2, 'presented': 48}]`.
- Tried and reverted, so nobody repeats it blind: id-only material hashes, grey albedo for a missing file
  (`albedoConstant` 0.5), and a `refresh_materials()` driven by a path-arrival flag. It halved the rebuilds (3 -> 2) and
  broke `test_live_normal_map.py`, because a material created before its normal/metal files land never received them.

**The obstacle, measured:** when a texture readback is **deferred** (per-frame budget exhausted) the texture has **no id
yet**, so the draw arrives with `texture = 0`, `material_for` returns null, and the geometry is rebuilt when the id
appears — 48 frames later in the mock. The fix is to **reserve the texture id at first sight** and retry the readback
for it, so the id, and therefore the material hash, exists from the first frame; everything downstream of that (grey
albedo, swap-on-arrival) is written and was green apart from that case. That is the next piece of work, not a redesign.

**The mechanism works, and the switch is the mistake I made.** With the full change in (id reservation, grey albedo,
id-only hash, no wait, per-submit refresh) `checks/gate_live_late_material.py` **passes**: one build per geometry, no
texture-triggered rebuild, and a `CreateMaterial -> DestroyMaterial -> CreateMaterial` triple under an unchanged hash
with different arguments. Four gates then failed (`test_live_late_files`, `test_live_normal_map`, `test_live_geometry`,
`test_live_texture_writer`) because they freeze the *opposite* contract: "a mesh is not built until its files land". That
is the plan's own rule asking to be obeyed - **new behaviour behind a switch, default off, until the user picks it from a
sheet** - and I applied it globally instead, twice. Every experiment was reverted; **suite 86/86** (`runtime/suite-s31`).

Four facts that cost the most time and will save it next time:

1. **A deferred readback has no id**, so the draw arrives with `texture = 0` and is rebuilt when the id appears. Reserving
   the id at first sight (`deferred_readbacks()` in `live_capture.h`) fixes it, and the retry must read the **resource
   once** even when two kinds (metallic, roughness) come from one mask, or `pbr-budget-one`'s "one staging copy" check
   fails - a real regression, caught by a gate rather than by me.
2. **`State::landed` means "the file is on disk"**, not "a path was handed over at capture time" (`texture_paths` is
   filled when the capture is queued). Passing a path from `texture_paths` early is what the fake runtime flags as
   `VIOLATION CreateMaterial names live_N.dds, which is not on disk`.
3. **`refresh_incomplete_materials` must reuse the material's own `hash`, not the map key** (`key` mixes the ids and is
   not what the runtime knows the material by). Passing `entry.first` created orphan materials under hash 1 and 2: the
   mesh kept a destroyed handle and the new material was never referenced.

#### T3 findings (2026-11-13, source read this session)

- **Instance identity** is the hash of mesh handle, material hash, bone hash, category, particle desc, instancing hash,
  texgen mode, the two shader flags, z-write/z-enable, sky flag, `objectToWorld` and `textureTransform`
  (`rtx_scene_manager.cpp:91-134`, read). So a re-posed mesh with a new handle is a **new instance**: zero motion on its
  first frame (`rtx_instance_manager.cpp:272-275`, scout).
- **Previous vertex positions are not only for bone-skinned meshes.** `ObjectCacheState::kUpdateBVH`
  (`rtx_scene_manager.cpp:512-544`, read this session) keeps a **history buffer pair**, swaps it on every update and
  assigns `previousPositionBuffer` from the other slice. The scout claim in section 11.5 is therefore too narrow: any
  object Remix is *updating* gets previous positions.
- **But the API cannot update a live mesh**: a repeated `CreateMesh` under a live handle is ignored and the new vertices
  are dropped (`rtx_asset_replacer.cpp:243-247`, read by the lead). So a pose we re-upload as a new mesh handle can never
  reach the history path, and previous positions are only available when **Remix itself** skins the mesh from bone
  transforms.
- **Consequence, and the only route:** `NIER_REMIX_LIVE_GPU_SKIN=1` (bind-space mesh moved by the CB11 palette) is the
  only way to get real per-vertex motion for animated characters; the CPU-bake path cannot have it, whatever we do with
  materials.
- **Measured 2026-11-13, same route and same place, 8 s turn in the camp:**

| | `pose=` rebuilds | `buffer_skinned=` | `built=` |
|---|---:|---:|---:|
| CPU bake (default), `t3-skin-off` | **70,415** | 2,074 | ~74k |
| `NIER_REMIX_LIVE_GPU_SKIN=1`, `t3-skin-on` | **0** | 2,617 | ~16k |

  So skinning on the GPU removes the entire pose-rebuild stream - the largest single source of mesh churn in a live run -
  and it is the only path with previous vertex positions. What is left is `buffer=`/`buffer_dynamic=` churn (13-14k), which
  is the dynamic-vertex path and a separate item. Open question before flipping the default: the picture must not regress
  (the CPU bake is the shipped path today), so the A/B with shots at the same moment is the next run.

#### S1. Exit hang

**Symptom.** With the real runtime loaded, `ExitProcess` waited 230 to 322 s (`t2-unorm-41686139` rendered all
2,500 frames and then timed out). The replayer normally uses `TerminateProcess`, which hides it. In the game it
would be a hang on quit.

**Hypothesis (scout, source lines checked for the loop itself):** `RtxInitializer::waitForShaderPrewarm`
(`rtx_initializer.cpp:201-209`) loops `while (isCompilingShaders()) Sleep(1)` with no timeout, and is called
from `onDestroy` (`:57`) before the compiler threads are told to stop. `remixapi_Shutdown` releases the device,
which runs that path. Other waits without a timeout on the exit path are listed in section 7.

**Steps.**
1. Reproduce on purpose: run the replayer with a normal exit (find the switch in `capture_replay.cpp`, or add
   `REPLAY_EXIT=clean`) for 300 frames and for 2,500 frames. Record seconds from last frame to process end, and
   whether we call `Shutdown`, in what order, from which thread (`remix_live.cpp` teardown).
2. While it hangs, take thread stacks (`winedbg --command "bt all"` attached to the pid in the replay prefix, or
   Proton's equivalent). The stack names the wait.
3. If it is the prewarm loop: the exit takes as long as the shader queue. Options, in order: skip `Shutdown`
   and terminate after releasing our own objects (what a game crash handler does), or wait for
   `isCompilingShaders` to finish at startup behind the loading screen instead of at exit. Check whether an
   `rtx.conf` key limits prewarm (`rtx.shader.*`: look in `rtx_options.h`, do not guess the name).
4. Gate: the fake runtime's `Shutdown` sleeps N seconds when asked (`FAKE_REMIX_SLOW_SHUTDOWN`), and the proxy's
   exit path must finish within a bound.

**Done when.** A clean exit from replay ends within 10 s with the real runtime, or the cause is recorded with a
stack and the chosen workaround is gated. Confirm with the real game's quit time once G5 runs.

#### S1 result so far (2026-11-13, this session)

the CRT runs the DLL detaches. That reproduces the hang the plan describes.

  renders and presents all 300 frames and then **never exits** — the run hit its 146 s timeout with `presented=300`. The

  teardown wait, which fits `RtxInitializer::waitForShaderPrewarm` (a `while (isCompilingShaders()) Sleep(1)` with no

- **The thread stack needs the user's permission.** `kernel.yama.ptrace_scope` is **1**, so `gdb -p` on the hung process

  the cache is not what prewarm waits for, or the wait is in another teardown path (section 11.6 lists a fence retry and

- **It is a deadlock, not a slow wait.** `s1-long` ran 422 s with all 300 frames presented and still did not exit. The

- **It is in Remix's teardown, not in the replayer or the proxy.** `--mode off` (proxy loaded, Remix not started) with
  `REPLAY_EXIT=clean` **exits in 4.1 s** for 120 frames. The same replayer with Remix on never exits. That narrows S1 to
  the runtime's destroy path and means the practical mitigation is already known: a client that never calls
  `remixapi_Shutdown` (or exits without running the device destructor) does not hang - which is what the replayer's

- Next: with the user's permission (`ptrace_scope` is 1) attach to the stuck process and name the wait; without it, the
  measurable question left is whether skipping `Shutdown` in a *real* run leaves the process clean for the next run
  (`s1-no-shutdown`: same run, `Shutdown` skipped, exit code and next-run behaviour recorded).

### 11.4 Remix textures and changing a material (scout 2026-11-13, `research-2026-11-13/remix_material_swap.md`)

- A mesh stores its material **handle**. The material is looked up on **every draw**
  (`rtx_scene_manager.cpp:2577`, read by the lead). A missing one gives the default material, not a crash (`:2590`).
- `CreateMaterial` with a hash that exists is **ignored** (`rtx_asset_replacer.cpp:222-227`, read by the lead).
  The paths in the ignored call are still preloaded (`rtx_remix_api.cpp:897-900`).
- `CreateMesh` with a handle that exists is ignored too, and the new vertex data is dropped (`:243-247`, read).
- So "this material now has file X" is: write X, `DestroyMaterial(H)`, `CreateMaterial` with the same hash and the
  full info. Both calls go through the same command queue. The meshes are not touched.
- Textures must be **DDS files on disk**. There is no upload-from-memory entry in the interface table
  (`rtx_remix_api.cpp:1784-1797`, `rtx_asset_data_manager.cpp:620-633`).
- The header is read synchronously on the command thread, the pixels are uploaded asynchronously
  (`rtx_texture_manager.cpp:1517-1567`). What the shader shows for a not-yet-resident texture was not traced.
- A file that is **missing when the material is created is never retried**. No watch is placed on it.
- The surface-material cache keys on the material hash and a texture-presence mask
  (`rtx_scene_manager.cpp:1665-1694`), so a swapped material should produce a new surface material. Not tested.

### 11.5 Remix instances and motion (scout 2026-11-13, `research-2026-11-13/remix_instance_motion.md`)

- There is no instance id in the API. Identity is a hash of the mesh handle, the material hash, bones, camera
  type, categories, `objectToWorld` and the texture transform (`rtx_scene_manager.cpp:91-134`). If that misses,
  the same mesh handle is matched to the nearest existing instance within `uniqueObjectDistance`, default 300
  units (`rtx_draw_call_tracker.cpp:232-305`, `rtx_options.h:525`). Otherwise it is a new instance.
- The previous transform is internal: last frame's `objectToWorld`. A new instance starts with previous equal to
  current, so zero motion on its first frame (`rtx_instance_manager.cpp:272-275, 324-325, 1206-1225`).
- Previous **vertex positions** exist only for meshes the runtime skins itself from bone transforms
  (`rtx_scene_manager.cpp:452, 512-544`). Re-uploaded pre-skinned geometry gets object motion only.
- Destroying a mesh removes its instances at once (`rtx_scene_manager.cpp:2625-2627`). Re-creating a mesh on a
  texture change therefore costs identity, a full BLAS build and, for skinned meshes, that frame's history.
- History is reset only globally (render mode change, camera cut), not per instance (`rtx_context.cpp:392-418`).
- Keep the mesh handle stable. The material swap of 11.4 does not change the instance key (the key uses the
  draw's legacy material hash, taken before the API material is applied: `:2556-2562`). Inferred, not tested.

### 11.6 Remix exit path (scout 2026-11-13, `research-2026-11-13/remix_exit_path.md`)

- `remixapi_Shutdown` joins nothing itself. It releases the D3D9 device until its count is 0, then the interface,
  then shuts Sentry down with a 4 s cap (`rtx_remix_api.cpp:1671-1693`, `util_sentry.cpp:82`).
- The waits are in the destructors that run inside those releases. `RtxInitializer::onDestroy` calls
  `waitForShaderPrewarm`, which loops `while (isCompilingShaders()) Sleep(1)` with **no timeout**
  (`rtx_initializer.cpp:57, 201-209`, read by the lead). The compiler threads are told to stop only later
  (`dxvk_device.cpp:167`). This is the leading explanation for the 230 to 322 s exit. **Not confirmed by a stack.**
- Other waits without a timeout on the same path: `vkDeviceWaitIdle` (`dxvk_device.cpp:486`), a fence wait that
  retries forever (`dxvk_cmdlist.cpp:173-177`), the submit and finish thread joins (`dxvk_queue.cpp:57-58`),
  `dxvk::thread::join` is `INFINITE` (`util/thread.cpp:38`).
- There is no `DllMain` in the runtime. A plain `ExitProcess` without `Shutdown` should not run the device
  destructor at all, so if the hang appears without a `Shutdown` call, look at static destructors
  (`DxvkDeferredOpFinalizer`, `dxvk_raytracing.cpp:102-119`). Inferred.
- Expected order for a client: `InitializeLibrary`, `Startup`, `Present` per frame, `Shutdown` once.

### 11.7 Remix sky, tone mapping, presentation (scout, `research-2026-11-12/`)

- **Sky:** an API instance in the SKY category is hidden from the traced scene (`rtx_instance_manager.cpp:1047-1050,
  1348-1349`). The game-sky path runs only for D3D9 draws (`rtx_context.cpp:1018, 2366`). No API path fills the
  sky probe. Sky radiance is `skyBrightness` times the probe (`composite.comp.slang:631`). The dome light is the
  working route.
- **Tone mapping defaults:** mode Local, `useLegacyACES` true (`rtx_options.h:1181-1188`). Local: exposure 0.75,
  shadows 2.0, highlights 4.0, finalize with ACES true (`rtx_local_tone_mapping.h:67-72`). Global: dynamic range
  15, curve -24 to 8 stops, exposure bias 0, colour grading off, contrast and saturation 1
  (`rtx_tone_mapping.h:103-120`). Auto exposure on, speed 5, EV -2 to 5, median metering
  (`rtx_auto_exposure.h:76-84`). User brightness 50 is 0 EV.
- **Presentation:** `CopyRenderingOutput(FINAL_COLOR)` blits back buffer 0 into the caller's surface, queued.
  Vsync is not forced (`PresentationInterval` 0 at startup). `rtx.reflexMode` defaults to LowLatency and adds a
  CPU sleep in Present (`remix_present_copy.md`).
- **FSR4 on the Remix frame** needs depth and motion vectors we do not export (`fsr4_redstone.md`). Parked.

### 11.8 The game: shaders, constants, captures

- **Main lit family** (for example `0c2a34…`): `cb1[0]` holds flags. `.x` use the normal map, else flat. `.y`
  albedo is `cb1[4].xyz`. `.z` gloss is `cb1[5].x`. `.w` metal is `cb1[5].y`. About 470 scene draws over the
  desktop captures have `.z` or `.w` set, and their bound mask is a 32x32 placeholder (measured, README).
- **Roles in that family**, as the tracer names them: albedo slot 0 rgb, metal slot 1 or 2 `.x`, gloss the same
  slot `.y` (inverted to roughness), normal slot 2 or 3 rgb, **detail normal slot 3 or 4 `.xy`** on its own
  tiling. Sending the detail normal as the main normal gave blotchy, wet-looking surfaces (`PBR_MAPPING.md`).
- **Slots that are never a material:** 11 shadow, 12 and 19 fog tables, 13 depth, 14 dither, 17 screen-space AO,
  18 cube maps (`pbr_trace.py`, `MATERIAL_SLOTS`).
- **Tint:** the game multiplies albedo by `cb4` times `cb8[instance]`, and by a second-UV texture. Neither is
  sent (`PBR_MAPPING.md`).
- **Terrain and ground blend family** (`f85282…`, `f7a8a9…`): slot 0 repeat is `cb1[5].xy` (captured values 1, 5,
  10, 25, 45), layers 1 and 2 use `cb1[5].zw` and `cb1[6].xy`, vertex colour sets the weights. No traced roles.
  The per-draw UV bake exists (`uv_bits`), and the `uv:0:cb1[5].xy=1,1` log line is per shader from its first
  draw, not a sign that the bake fails (closed 2026-11-12).
- **How the tracer finds roles** (`checks/pbr_trace.py`, method in `PBR_MAPPING.md`): forward provenance per
  register component, then the shader's own lighting maths names the role. Metal is the factor of the F0 lerp
  against `0.03` or `0.08`. Albedo is that lerp's base. Gloss is the `(1 - g)²` feeding the GGX alpha clamp at
  `1e-3`. Normal is a sample followed by `- 0.5`. Detail is a sample followed by `* 2 - 1` on two lanes. A role
  that cannot be pinned to one channel is left out, never guessed.
- **Tracer coverage** over the 605 live pixel shaders (`evidence/remix-current/2026-11-01/material-roles-coverage.md`):

| | albedo | metal | gloss | normal | detail | all four |
|---|---:|---:|---:|---:|---:|---:|
| shaders with the role pinned | 104 | 102 | 94 | 111 | 103 | 61 |

| class of the 473 shaders with no role | count |
|---|---:|
| samples a material slot, no lighting maths (unlit or albedo only) | 228 |
| lit, samples a material slot, roles not pinnable (the real gap) | 218 |
| no texture sample at all | 16 |
| samples only excluded slots | 11 |

  Slot 0 is the traced albedo in 100 of 104 cases, and 432 of the 501 shaders without a traced albedo sample
  slot 0 first: that is what justifies the "first usable texture in slots 0 to 15" fallback. Widening the F0
  literal search was measured and rejected (only 17 and 21 of the 218 carry `0.03` or `0.08`). An
  output-provenance fallback was measured and rejected (agreed on 32 of 104).
- **What an F9 capture holds** (`frame_<id>/`): `frame.json` (draw count, `min_index_count` 128, texture count),
  `draw_<n>/capture.json` (index and vertex layout, `vs_hash`, `ps_hash`, `state` with blend, depth and cull,
  `ps_textures` slot to id, `ps_cbs` slot to size), the draw's vertex, index and constant buffers as `.bin`,
  `textures/tex_<id>.dds`, `lights.json` with `lights_t20.bin` and `lights_t22.bin`, and pixel shader bytecode in
  the shared `shaders/` folder. **It does not hold** vertex shader bytecode, the game's final picture, draws under
  128 indices (so no post passes and no colour grade), or full mip chains.
- **Replay consequence:** with no vertex shaders, the replayer runs a generated one that puts every vertex at
  the origin. Nothing is rasterised and the game's own picture cannot be reproduced from a capture. The proxy
  reads state on the CPU and never needs the rasterised result (`replay/capture_replay.cpp`, header).

## 12. Method: how the work is done and checked

### 12.1 The loop for one item

1. **Number first.** Produce the number that shows the problem, with the tool and the run label, and write it
   in the item. If the number cannot be produced, the item is an investigation and ends in a table, not in code.
2. **Gate.** Write the test that fails today for the reason the item names. Run it and see it fail.
3. **Change**, behind a switch that defaults to off. Smallest diff that turns the gate green.
4. **Mutation.** Revert the change (or flip the switch) and see the gate go red again. A gate that stays green
   proves nothing. `shim-incomplete` was checked this way. **Not yet checked this way:** the relaxed `open` counter
   in `test_live_map_redirect.py` (does a real leak still fail it) and `test_live_albedo_tag.py` beyond its own
   on/off pair. Do both before building on them.
5. **Suite.** `run_suite_parallel.py` in a fresh folder, all green.
6. **Replay**, real runtime, the three reference captures: frame rate against the guard, shot against the last
   accepted shot.
7. **Sheet** for the user where the change is visible. The default flips only after the user picks.
8. **Review** by a `reviewer` agent on the whole diff. Fix or record each finding with a reason.
9. **Write down**: Status cell here, numbers in `replay/README.md`, a dated entry in `PROGRESS.md`.

### 12.2 Four levels of test, and what each one proves

| Level | Command | Time | Proves | Does not prove |
|---|---|---|---|---|
| Mock gate | `python3 checks/test_<name>.py` | 0.5 to 3 min | Our logic on a constructed case: which calls reach the runtime, with which bytes. Runs a small D3D11 program (`menu_overlay_mock_game.cpp`) under Wine, Xvfb and llvmpipe against a fake runtime that logs every call | Anything about NieR's real data or the real path tracer |
| Replay, fake | `run_replay.py <label> <capture> --mode fake --frames 400` | 1 to 3 min, no GPU | What we send for a **real** game frame, as text (`fake-remix.log`). Input of the scoreboard | The picture |
| Replay, real | `run_replay.py <label> <capture> --frames 2500` | 1 to 3 min, 6800 XT | The picture and the frame rate with the real runtime | Motion, the game's own picture, the laptop |
| Game run | Track G, not built | | Motion, loading, quit, the game's picture | Other scenes, the laptop |

Use the cheapest level that can show the thing. Most look items need all of the first three.

### 12.3 Writing a mock gate

- Copy the shape of an existing one: `checks/test_live_albedo_tag.py` (new, small) or
  `checks/test_live_map_redirect.py`. A gate re-runs itself inside `xvfb-run` with a private Wine prefix under
  `runtime/<gate-name>/`, builds the mock and the fake runtime with mingw (`-Wall -Wextra -Werror`), runs cases
  through `test_remix_live.run(work, name, env)`, and writes `validation.json`.
- **Every environment variable a gate sets must be in `ENV_KEYS`** (`checks/test_remix_live.py:32`, extended per
  gate). The runner strips those keys from the inherited environment first, so a key missing from the list can
  leak from the shell or from another gate. Five were added on 2026-11-13 for that reason.
- The mock grows by switches: `MOCK_<NAME>` in `menu_overlay_mock_game.cpp` builds the case (for example
  `MOCK_PBR_PS` the lit shader, `MOCK_TEX_SRGB` an sRGB-tagged albedo, `MOCK_MAP_TWICE` a double map).
- The fake runtime (`remix_live_fake_runtime.cpp`) logs `CreateMaterial`, `CreateMesh` and instances, and writes
  a line starting `VIOLATION` when a call would be wrong in the real runtime (for example a material naming a
  file that is not complete on disk). Every gate asserts that no `VIOLATION` appears. **When the real runtime is
  found to behave in a way the fake does not model, teach the fake first** (T1 step 1 is an example: the real
  runtime ignores a repeated `CreateMaterial`, the fake accepts it).
- Assert on bytes and counts, not on a header alone, and name the first mismatch in the message.
- A counter printed by the worker thread can be read mid-frame. Take the settled value (lowest or last of
  several windows), not one sample: `test_live_map_redirect.py` failed once under suite load for this reason.
- Add the new gate to the suite the way the others are listed, and say in its docstring what it cannot prove.

### 12.4 Measuring frame rate

- 2,500 frames, one capture, one change per run. Read `steady_fps_median` and `steady_ms` in `summary.json`.
- Two builds that should perform the same differ by about 1% (30632051: 29.3 on `3c487b0a`, 29.0 on `3878183a`.
  41686139: 43.9 and 42.9. 23275488: 50.4 and 49.3). A difference under 3% is not a result. Repeat a run before
  believing a small win.
- **One job on the GPU at a time.** A replay beside another replay, a suite run or a game gives numbers that mean
  nothing. The suite uses llvmpipe (CPU), and 24 lanes of it still slow the replayer's thread.
- `--mode off` gives the replayer's own cost. Subtract it before blaming the proxy.
- `--env NIER_REMIX_LIVE_PROFILE=1` adds `remix: live observe us/frame state= ia= key= material= rest=` lines.
  `--env REPLAY_PROFILE=1` adds the D3D11 call-group split to `replay-result.txt`.
- The replayer ends with `TerminateProcess`, so replay never shows the exit hang unless asked (S1).
- Confs for one-key runs live in `runtime/replay/confs/<name>.conf`: copy `deploy/rtx/desktop-replay.conf`, add
  the key, pass `--conf`. Keep `rtx.dlssPreset = 2` in every one.

### 12.5 Measuring the picture

- `frame_tools.py stats` gives median luma, 95th percentile, clipped and crushed share, mean saturation. They rank
  candidates and catch blown or crushed frames. They do not say which picture is right.
- `frame_tools.py diff` between two shots of the same capture and frame: 1.1 to 1.5 grey levels is denoiser
  noise between identical runs (measured: 1.52 between `n1-base-30632051` and `t2-unorm-30632051`, same settings).
  Normal maps on gave 5.55. Under 2 means "unchanged".
- `frame_tools.py sheet` builds the labelled side-by-side the user picks from, and refuses panels of different
  size. Use `--crop` for the region where the change shows. Always the same capture and the same frame.
- An agent looks at a shot through `replay/view.py` (a small JPEG) and the Read tool with `offset=1`. An agent's
  look finds gross faults (white blobs, missing objects, black frames). It does not settle taste.
- The stats line and the scoreboard are checked against each other: the `untextured=0` counter disagrees with
  the 16% null-material row, which is a bug in the counter (L4 step 5).

### 12.6 The material scoreboard

`replay/material_scoreboard.py <id>` reads `runtime/replay/n1-fake-<id>/fake-remix.log`. It keeps the last
`CreateMesh` per capture key and joins it to its `CreateMaterial` by handle, then sums triangles per class. A mask
of 32 pixels or less on its first side is counted as a placeholder (a heuristic: L3 replaces it with the game's
own flag). It reads 400 frames. On the two captures run so far the last `CreateMesh` and `CreateMaterial` come
by frame 80, so 400 is enough: check that again on a new capture. Rerun it after every
material item, and put the before and after rows in the item.

### 12.7 Reading the runtime source

- The source is at `analysis/runtime/src/dxvk-remix` (remix-1.6.1). `rtx_options.h` declares every `rtx.*` key
  with its default: look a key up there before putting it in a conf.
- Scout brief that worked (three ran in parallel on 2026-11-13, 183 s): one question per agent, read-only, "every
  claim needs a file path, a line number and a one-line quote of the code", "if you cannot find it say not found
  and list what you searched, do not guess", an answer first and the evidence after, 60 lines at most.
- **A scout's answer is a lead.** Before a change depends on a claim, open the lines. Section 7 lists which were
  opened. Of the claims opened so far, all held, and the reports mark their own inferences as inferences.
- Through the `workflow` tool a scout needs its model named explicitly (`anthropic/claude-haiku-5-5` on this
  provider). The `subagent` tool picks it by itself.

### 12.8 Handing work to other models (`/skill:local-delegation`, read it first)

- Only **gated** code goes to a local model: the frozen gate is the brief. Prose specs for logic have failed with
  local models every time they were tried.
- Never accept "passed" from a worker. Rerun the gate.
- One writer per file at a time. `live_capture.h` and `live_scene.h` are touched by T1, L3, L4 and L6.
- Edits to existing prose and documents stay with the lead: local models retype characters and exact-match edits fail.
- Log every delegated task in the ledger, `~/Documents/Local-Model-Delegation-Outcomes.jsonl`.
- Skip delegation when the brief takes longer to write than the task.

### 12.9 Safety rules that held this far

- Nothing is committed or pushed without the user asking. `git status` before edits.
- The game folder is written only by the installer and by the game (constraint 2). The capture folder is read.
- No package is installed. No system setting is changed.
- A background job is ended by its own process group, and nothing that was not started here is killed.
- Temporary files in `/tmp` are lost on reboot: anything a later reader needs is copied into the repository
  (`replay/research-<date>/`).
