# Research: adopting Remix Plus for NieR's D3D11 remixapi host

## Summary
**GO for an isolated, pinned Remix Plus v2 probe; NO-GO for replacing the installed runtime or D3D11 stack now.** The first useful migration is stable meshes with four-bone API skinning, followed by same-hash morph refresh—not an interop rewrite. The advertised shared D3D11 output handle is a failure stub in both inspected forks; swapping the DLL alone will not remove our output readback.

Read-only evaluation: read both requested notes, current PROGRESS.md checkpoint, README, INTEROP_API.md, LIVE_TRANSFER.md and the beginning of analysis/checks/remix_live.cpp. No game launch, render, install, binary download, build or project edit occurred. Findings below distinguish source evidence from proposed experiments.

### 2. Artifacts, architecture and licensing
**Claim:** Windows x64 is the evidenced Plus target; Linux-native and released Plus ARM64EC support are not established. **Support: direct evidence for published assets/build configuration; interpretation for suitability; confidence: high/medium respectively.**

- Canonical [release metadata](https://api.github.com/repos/RemixProjGroup/dxvk-remix/releases) lists only [Remix_Plus_v2.0.0.zip](https://github.com/RemixProjGroup/dxvk-remix/releases/download/remix-plus-2.0.0/Remix_Plus_v2.0.0.zip) (474,489,346 bytes) and its [checksum file](https://github.com/RemixProjGroup/dxvk-remix/releases/download/remix-plus-2.0.0/Remix_Plus_v2.0.0.zip.sha256). API digest: `4abe3f17b1ff5bdc27efe620a29c22030a252fb85edd4ce024ee45fc3be1a329`. Release says it contains runtime, **32-bit bridge**, API headers/docs and licenses. Archive contents/PE types were **not** inspected.
- [v2 README](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/README.md): “Only x64 Windows is built and tested.” Source builds produce 64-bit `d3d9.dll`; the bridge is x86 client → x64 server, not an available x64 IPC client for NieR. Full dependencies beside the runtime are required; do not test a lone copied DLL.
- [v2 CI](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/.github/workflows/build.yml) builds on Windows, uploads `rtx-remix-for-x64-games-...` and x86-game bridge packages. No Linux-native artifact is evidenced. Running Windows PE DLLs with Wine/Proton is a separate compatibility experiment, **not** a native Linux release. D3D11/DXGI modules require explicit `-Denable_d3d11=true -Denable_dxgi=true`; both are off by default, so do not assume the release zip supplies this host stack.
- Source retains [build-wina64.txt](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/build-wina64.txt), [build-wina64ec.txt](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/build-wina64ec.txt), and an ARM build script. These are **build scaffolding, not evidence of a working or released ARM runtime/dependency set**. No Plus ARM64, ARM64EC or ARM64X release asset was verified. NightSight has no published release assets in the inspected Releases API; no Linux/ARM alternative was established there.
- [NVIDIA upstream 1.6.1 release metadata](https://api.github.com/repos/NVIDIAGameWorks/rtx-remix/releases/tags/remix-1.6.1) does list ARM64-named packages and release notes discuss ARM64/ARM64EC. That does not identify every DLL inside those packages and does not confer support on Plus. Keep upstream ARM investigation separate.
- Architecture gate: [Microsoft ARM64EC](https://learn.microsoft.com/en-us/windows/arm/arm64ec) says ARM64EC code can interoperate with emulated x64 in one Windows 11 process; [ARM64X](https://learn.microsoft.com/en-us/windows/arm/arm64x-pe) combines classic ARM64 and ARM64EC compatibility. **Plain PE ARM64 is not proof of x64-loadable ARM64EC/ARM64X.** Before any laptop loader test, inspect Machine plus hybrid/load-configuration metadata and dependency architectures; an ARM64 filename or build config is insufficient. Windows EC compatibility also does not prove equivalent behavior under Linux/Wine/emulation.

**Licensing (direct evidence; high confidence, not legal clearance):** [v2 README licenses](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/README.md), [LICENSE](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/LICENSE), [LICENSE-MIT](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/LICENSE-MIT), [CREDITS](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/CREDITS.md): DXVK zlib; NVIDIA Remix MIT; NUMOS Apache-2.0; contributions attributed file-by-file. ### 3. ABI: rebuild a separate Plus caller; never change only the version number
**Claim:** Our stock 0.6.x caller cannot safely use Plus's interface table. **Sources:** [v2 header](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/public/include/remix/remix_c.h), [migration guide](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/docs/RemixApi-Migration.md), [implementation](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/src/dxvk/rtx_render/rtx_remix_api.cpp), [stock header](https://github.com/NVIDIAGameWorks/dxvk-remix/blob/main/public/include/remix/remix_c.h). **Support: direct evidence; confidence: high.**

- v2 `isVersionCompatible` accepts 1.x callers with matching major and caller minor ≤ runtime minor, plus legacy **0.1000.x**. It rejects NVIDIA **0.6.x**. FNV remains the 0.1000.1 line. Conversely our installed stock gate, documented by local binary inspection in INTEROP_API.md, expects 0.6.x; a Plus-built caller is rejected there. Do not spoof versions to bypass either gate.
- Guide: interface table is **41 pointers / 328 bytes on x64**, “It is not NVIDIA's layout.” Fork additions are **inserted among stock slots**, not merely appended. Compile the Plus-specific host translation units with the exact release header and keep the stock caller/header in a separate build target. Resolve optional named exports only from that same loaded module; check pointers and feature versions, not just initialization success.
- Direct header comparison: `HardcodedVertex` stays 64 bytes; `MeshInfo` retains sType/pNext/hash/surface pointer/count; surface retains vertex/index pointer+64-bit counts, optional skinning and material handle. Skinning public arrays are float weights and uint32 indices, totals `V * bonesPerVertex`. Existing CreateMesh data construction is broadly source-compatible, **not binary-table compatible**.
- `MaterialInfo` retains texture paths/hash/emissive/sprite/filter/wrap inputs. `MaterialInfoOpaqueEXT` includes albedo/opacity/roughness/metallic constants, thin-film and alpha state, height/displace fields and trailing `enableDlssControlMask`, intensity/tone/structural strengths. Zero-initialize the exact new type and set fields by name; don't copy a hand-sized old struct. 0.1000.0 callers receive defaults for the newer control-mask tail. The inspected current stock header also contains the control-mask additions; the mismatch is not simply “Plus has more material fields.”
- Category ABI matches upstream by explicit values: WORLD_UI bit 0, SKY 2, TERRAIN 16, ANIMATED_WATER 17, third-person model/body 18/19, IGNORE_TRANSPARENCY_LAYER 22 (deprecated/ignored), VIEW_MODEL 26. Preserve the public enum, never map via internal ordinal order. Add small compile-time layout/bit assertions to the future probe, plus a stock-versus-Plus rejection test.

### 4. Features that actually justify evaluation
**Claim:** Four-bone skinning and stable-hash morph refresh directly address our measured mesh-rebuild problem. **Support: direct source evidence; benefit to NieR is researcher inference; confidence: high for implementation, unmeasured for benefit.**

- [v2 mesh implementation](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/src/dxvk/rtx_render/rtx_remix_api.cpp) fixes immediate **and deferred** paths: weight stride `sizeof(float) * bonesPerVertex`; compressed-index stride `sizeof(uint32_t) * divCeil(bonesPerVertex, 4u)`. FNV has the same fix. [Stock implementation](https://github.com/NVIDIAGameWorks/dxvk-remix/blob/main/src/dxvk/rtx_render/rtx_remix_api.cpp) uses one-float weight stride. This settles the requested runtime-side four-bone fix, not just FO4's successful call pattern.
- [skinning shader](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/src/dxvk/shaders/rtx/pass/skinning.h) derives the last weight as `1 - sum(previous weights)`. Supply normalized four-element rows and four uint32 indices per vertex, counts ≥ V×4, and enough bone matrices for every referenced index (palette bounded by runtime limits). Runtime input checks can repair/drop malformed data; do not rely on repairs for correctness.
- `MeshInfoRefreshGeometryEXT` chains onto CreateMesh under the **existing hash**. Header: “refresh is ignored ... if no mesh is registered ... or if the surface count differs.” Intended for unchanged-topology morphs; preserves previous-position data/motion history. Ordinary repeated live-hash creates still succeed without replacing geometry. Keep new-hash-first replacement for topology changes and stock fallback; do not use refresh as arbitrary mesh mutation.
- In-memory `CreateTexture`: packed mip pixels, dimensions/format/data size/hash; curated RGBA/BGRA UNORM/SRGB and BC1/3/5/7. Materials reference its synthetic hash path. This removes our DDS-file round trip **after we already have CPU pixels**; it does not magically remove D3D11 texture readback. GPU Prepare/Import is a different, restricted path.

Local PROGRESS.md corrects the old performance rationale: “readback 152 ms” was worker output-readback **including wait for Remix's GPU frame**, not a measured 152 ms removable transfer. Stock top-2 skinning already matched one captured pose closely; animation and cost remain untested. Therefore measure Plus against that stock alternative, not only against the worst CPU-baked/churning baseline.

### 5. Output/HUD interop: what removes readback, and what does not
**Claim:** Native-driver D3D11 cannot use the direct Plus D3D11 host, and shared-output-handle presence is not capability. **Support: direct evidence; confidence: high.**

| Route | Actual constraint | Recommendation |
|---|---|---|
| `dxvk_GetSharedD3D11TextureHandle` | [v2 api_d3d9_device.cpp](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/src/frontends/api/api_d3d9_device.cpp): “A shared D3D11 back buffer is not implemented”; valid arguments return `GENERAL_FAILURE`. [FNV helper](https://github.com/Kim2091/dxvk-remix/blob/925d7ab6d9b38b334c7a2763dd4f23dd9cdceb68/src/dxvk/rtx_render/rtx_fork_api_entry.cpp) also returns failure. | **NO-GO** as native Windows GPU-copy shortcut. There is no working handle/synchronization contract to use here. |
| RegisterD3D11Device + RenderD3D11 | [host implementation](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/src/frontends/api/api_d3d11_host.cpp) dynamic-casts to **this fork's DXVK D3D11Device**, rejects native-driver devices. Destination must belong to registered device, be single-sample, one array layer, render-target bound. Commands use its immediate-context stream/lock; registration on render thread; selected swapchain Present ends the frame. | Removes output CPU round trip only after adopting a **coherent same-build Plus D3D11/DXGI runtime**, on Windows or potentially Proton. Stock Proton DXVK is not automatically compatible. Much larger migration than d3d9.dll alone. |
| GPU UI layers / texture Prepare+Import | Overlay validates same-device fork textures, single sample/layer, non-staging. Prepare queries private `IDXGIRemixTexture`, prepares a view against Remix's VkDevice; import queues a read barrier. Retain token until Import returns, then release. | No native-driver or arbitrary cross-device import. Same-build host can avoid UI/texture CPU readback too. No exported raw resource may be used without lifetime/order guarantees. |
| ConfigureExternalFrame | [frame-export source](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/src/dxvk/rtx_render/rtx_frame_export.cpp), [API docs](https://github.com/RemixProjGroup/dxvk-remix/blob/remix-plus-2.0.0/docs/RemixApi.md): Vulkan OPAQUE_WIN32 memory + **binary** ready/released semaphores; same physical-device UUID; dedicated allocation/import parameters; ownership transferred through EXTERNAL in GENERAL. Consumer waits ready, acquires, reads, releases and signals released every frame. | Real implemented Vulkan export, **not a DXGI D3D11 shared texture handle**. A Vulkan consumer could avoid CPU readback, but importing into our current D3D11 pipeline is new interop engineering, especially under Proton. Defer. |
| Separate Remix presentation/window | Avoids moving Remix output into game backbuffer, independent of native D3D11 registration. | Possible on stock too. Not first choice: our native HUD handoff already works; focus/overlay/compositor/UI integration would regress scope. |

External-frame restrictions: needs Win32 external-memory/semaphore extensions; fails for external-swapchain mode, MSAA or unsupported backbuffer format. Returns RGBA8 UNORM display-encoded output, not arbitrary HDR/depth or generated frames. Present waits for command submission, not GPU completion; a consumer that stops signaling stalls the GPU queue. Stop export before consumer exit; recreate on resize and close exported handle copies. No cross-adapter support is evidenced. Proton exposing these Win32 Vulkan extensions/import semantics is **unverified** here.

**Bottom line:** retaining native Windows driver D3D11 + current in-backbuffer HUD means keeping readback for the first Plus experiment. Under Proton, a same-build fork D3D11 host is the most direct potential zero-readback route, but risks our DXVK/FSR4/D3D12 sharing/WAX chain. Neither route justifies changing the installed stack before a standalone device test.

## Minimal gate and staged adoption (researcher recommendation)

**Stage 0 — isolated identity/ABI gate: GO.** Future standalone probe under `analysis/runtime/remix-plus-v2/`, explicit DLL path and controlled dependency search, private working/config/log/cache directory and disposable prefix where appropriate. No game-folder deployment, no existing runtime overwrite. First static-only: archive checksum, PE architecture/hybrid metadata, dependencies/imports/exports, header checksum, initialized table layout, license inventory. Then a non-presenting loader test can check InitializeLibrary, version rejection and optional export availability without creating a scene/window/device. This does **not** prove rendering, GPU interop or performance. A runtime load may still initialize dependencies or write logs; isolate those too. Nothing in the API requires installation into the actual game directory.

**Stage 1 — minimum laptop A/B, only after approval: GO conditional on Stage 0.** Reuse the existing captured 2B/skin-stride fixture and standalone probe, not NieR. Same recorded bone sequence, camera, resolution, texture set and explicitly equivalent upscaler/quality settings. Compare (A) stock stable-mesh top-2 bones, (B) Plus stable-mesh four bones, with CPU-baked four-bone reference for correctness. Warm up identically, then record fixed-duration p50/p95 CPU submit, GPU/frame and whole-frame timings, mesh create/destroy/residency counts and VRAM. Include two independently posed instances, frozen-pose/camera-only movement, changed poses, and several refreshes under one hash. Assert one mesh registration per actor after warmup (except intentional morph refresh), bounded resources, no scene-input repairs/rejections, no crashes or destroyed-hash reuse. Image/silhouette comparison must include movement/temporal artifacts, not one still. No claimed improvement threshold is evidence yet; agree a material time/quality improvement before the run, reject gains explained solely by Plus's different defaults.

**Stage 2 — smallest host adoption: conditional GO only if B beats A meaningfully.** Build a separate Plus host/proxy variant with its exact header; keep D3D9 output/readback and existing native HUD handoff. Introduce stable four-bone actor meshes/per-frame bones, then RefreshGeometry only for morphs. Retain CPU-skin/new-hash replacement as correctness fallback. Add in-memory textures only after the mesh win is demonstrated. Keep stock variant independently buildable/loadable; no two ABI tables in one guessed struct and no hot runtime switching.

**Stage 3 — zero-readback D3D11 experiment: deferred / NO-GO for installed game.** First build a standalone same-build Plus D3D11/DXGI device probe: register device, known-color target, RenderD3D11, same-device UI texture, resize and shutdown; assert native-driver/foreign-device rejection. Then repeat our existing D3D11↔D3D12 FSR sharing/fence checks against that fork. Only if it passes on the actual laptop/Proton configuration should host scheduling move from the current worker/published CPU pixels to the render-thread host command stream.

**Change scope if authorized later:** vendored header and build target; remix_live worker/init/output handling; live_scene mesh creation/replacement and skinning capture; scene/material/texture builders; fake-runtime ABI/behavior and skinning/morph tests; build/deploy manifests and runtime/config provenance. Stage 3 additionally reaches D3D11/DXGI chain, HUD replay, FSR D3D12 sharing and device/fence tests. No engine hooks, bridge port, ARM custom build, retained-static redesign, weather or new lighting feature is needed to prove the first win.

**Explicit fallback:** leave installed stock runtime/proxy, native HUD, launch chain, FSR4 and existing off-by-default switches untouched. Prefer stock top-2 API skinning if it achieves equivalent animation quality/cost; Plus four-bone support alone is not a reason to incur an unmeasured hard-fork maintenance cost.

## Contradictions
- Prior notes say 0.1000.1 is current Plus; it is current FNV, **not release v2**, which is 1.0.0 with legacy compatibility.
- v2 API reference describes a shared NT D3D11 output handle, but implementation is a failure stub. Trust implementation; this disproves recommendation c2 in NEW_VEGAS_RTX_NOTES.md.
- General README wording “own D3D11 device” masks the fork/private-interface restriction. Native NVIDIA/AMD driver D3D11 is not accepted.
- Older notes describe a rebase-friendly fork; v2 README calls it a “hard fork ... does not rebase onto upstream.” Update/maintenance risk is larger than those notes imply.
- The old 150 ms readback interpretation is corrected in current local PROGRESS.md; don't promise that saving from changing the transfer mechanism.
